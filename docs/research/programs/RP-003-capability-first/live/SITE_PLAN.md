# RP-003 Site Plan

**Program:** Capability First  
**Status:** **Open** · **0 Complete**  
**Assigned observer/site/window:** none / none / none  
**Access basis:** [SITE_ACCESS_PACK](../../../templates/SITE_ACCESS_PACK.md) · **Evidence review:** [ARTIFACT_ACCEPTANCE_RUBRIC](../../../templates/ARTIFACT_ACCEPTANCE_RUBRIC.md)

## Objective and boundary

Observe whether capability-first mapping improves planning clarity over department-first roadmaps while preserving Cap≠Org and Capability≠Permission.

## Target observation points

1. Participants define capabilities by outcomes rather than department or job title.
2. Nodes, dependencies, ownership role classes, and evidence sources remain traceable.
3. L0–L4 maturity ratings have observable criteria and confidence.
4. A0–A4 automation affinity separates technical feasibility, risk, and approval need.
5. Duplicate/spanning capabilities across organization units are handled without hierarchy bias.
6. Capability and departmental roadmaps are compared under a declared rubric.
7. AI/workforce/evolution choices consume capability evidence without creating grants.
8. Ambiguous ownership and contested mappings remain visible.

## Required artifacts

1. Dated mapping agenda/session record and named cohort.
2. Authorized process, service, outcome, portfolio, and dependency source inventory.
3. Versioned capability graph/export.
4. Capability glossary and metamodel/instrument version.
5. Source-to-node/outcome/dependency trace.
6. Maturity and automation-affinity scoring rationale.
7. Department-roadmap comparison and decision-clarity rubric results.
8. Disagreement, exception, falsifier, provenance, integrity, and retention record.

## Dependency systems / contexts

1. Process/service catalog or approved source extract.
2. Portfolio/strategy/outcome evidence repository.
3. Organization reference source used only for comparison.
4. Graph modeling/version-control workspace.
5. Roadmap comparison and scoring workspace.

## Access and run sequence

1. Approve business scope, source systems, participant roles, and export/redaction methods.
2. Freeze metamodel and comparison rubric before mapping.
3. Observe graph construction, scoring, disagreement, and roadmap comparison.
4. Export immutable version and revoke temporary source/workspace access.

## Risks / ethics

1. Capability mapping used to rate individuals or justify restructuring; prohibit secondary personnel use.
2. Department power bias distorting nodes/ownership; preserve evidence and dissent.
3. Confidential strategy/portfolio leakage; minimize and use controlled handles.
4. Capability ownership interpreted as Permission/grant; fail closed.
5. Tool auto-layout/versioning obscuring changes; retain change history and source trace.
6. Comparison rubric chosen after results; freeze before observation.

## Exit conditions

1. Stop if source/participant access or consent is absent/revoked.
2. Stop if mapping collapses capability into department without a correctable trace.
3. Stop if any output is requested as permission, grant, or implementation instruction.
4. Return incomplete if graph version, source trace, or comparison evidence is unavailable.
5. RP-003 remains Open; no field session or score alone marks Complete.
